# Вход, сессии и владельцы

Реализованы SEC-02, SEC-03, OWN-01 и SEC-04. Проверки и ограничения фиксируются в `tasks/<ID>/verification.md`. Ручной сценарий: [manual-auth-check.md](manual-auth-check.md).

## Конфигурация и первоначальные аккаунты

Все настройки находятся в единственном `Soft/.env` для Development и Compose либо передаются окружением в Production. `JWT_SIGNING_KEY` — случайный секрет не короче 32 UTF-8 байт; `JWT_ISSUER`, `JWT_AUDIENCE` задают издателя и аудиторию; шаблон и Compose используют `aglomslag-local` и `aglomslag-clients`. `JWT_ACCESS_SECONDS`: 1..900, по умолчанию 300; `JWT_CLOCK_SKEW_SECONDS`: 0..60, по умолчанию 5; `JWT_REFRESH_DAYS`: 1..30, по умолчанию 7. Применяется только HS256. Смена signing key делает прежние access недействительными; refresh остаются в БД до отзыва/срока. `AUTH_LOGIN_LIMIT`: 1..1000, по умолчанию 20 проверок в минуту на реальный IP соединения, общий бюджет Login/refresh/смены пароля, включая отдельные aliases. За прокси без специальной настройки клиенты разделяют IP прокси.

Обычный запуск: заполнить `Soft/.env` и выполнить `docker compose --env-file Soft/.env -f Soft/Docker-compose.yml up -d --build`. После миграций и проверки обеих БД API автоматически выполняет идемпотентный `DemoUserBootstrap`. В Compose `DEMO_BOOTSTRAP=true` по умолчанию; вне Compose создание отключено, пока явно не задано `DEMO_BOOTSTRAP=true`.

`DEMO_USER_EMAIL/PASSWORD` создают пользователя `-1` (`Admin=false`), `DEMO_ADMIN_EMAIL/PASSWORD` — администратора `-2`. Пароли — 12..1024 символа. Повторный старт сохраняет существующие пароли и данные; изменение пароля в `.env` не является сбросом. Коллизия email, ID или роли завершает bootstrap с ошибкой и откатывает обе учётные записи. Прежний отключённый аккаунт `-1` с очищенным хешем может быть переинициализирован demo-bootstrap. У обеих ролей есть демонстрационный вариант; справочник принадлежит `-1`. Между Auth и SlagMode нет FK.

Endpoint Docker — `http://localhost:5000/graphql`, внутри контейнера порт `8080`; IDE — `http://localhost:5093/graphql`. HTTP доступен во всех окружениях, включая Production. GraphQL IDE в браузере, GET, SDL и introspection доступны публично. Бизнес-поля требуют JWT, кроме `login`; Login в соседнем поле не авторизует остальные поля документа.

## Необязательные операторские команды

Для обслуживания остаётся сервис `bootstrap` профиля `setup`. Штатный первый запуск не требует его вызова. Команда `docker compose --env-file Soft/.env -f Soft/Docker-compose.yml run --rm bootstrap` вручную повторяет demo-bootstrap.

Отдельное создание обычного пользователя: задать `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`, при необходимости `BOOTSTRAP_NAME`, затем `docker compose ... run --rm bootstrap --bootstrap-user` (здесь и далее `...` заменить на `--env-file Soft/.env -f Soft/Docker-compose.yml`). Существующий аккаунт эта команда не меняет. Пароль задаётся окружением, не аргументом командной строки. Удалить временные bootstrap/reset credentials из `.env` после применения, если они больше не нужны. Демонстрационные доступы остаются локальными настройками оператора.

## Пароли и обновление существующих БД

Identity V3 PasswordHasher: PBKDF2-HMAC-SHA512, 210000 итераций, случайная соль не менее 128 бит, версионированный формат. Новый пароль — 12..1024 символа, не только пробелы. Правильный устаревший Identity V3 хеш обновляется после успешной проверки; V2, plaintext и повреждённый формат не принимаются. Неизвестный/отключённый аккаунт проходит dummy-проверку с настроенной стоимостью. Ни пароль, ни хеш не входят в output пользователя, JWT или диагностические сообщения.

Миграция `SecureCredentials` **сбрасывает хеши и отключает существующие аккаунты**: прежний пароль `Password` больше не работает. Перед обновлением сохранить резервные копии обеих БД. Демонстрационный аккаунт восстанавливает автоматический demo-bootstrap; для остальных прежних пользователей нужен явный сброс: задать `TARGET_USER_ID` и `NEW_PASSWORD`, затем `docker compose ... run --rm bootstrap --reset-password`. Сброс также активирует отключённый аккаунт. Для блокировки: `TARGET_USER_ID`, команда `--disable-user`. Для себя доступна защищённая mutation `changePassword(currentPassword,newPassword)`, требующая прежний пароль. Пустой пароль не заменяет сохранённый.

PostgreSQL-триггер в миграции `RefreshSessions` отзывает все refresh пользователя в той же транзакции при изменении хеша или блокировке, включая rehash и доверенное операторское SQL. Повторное присваивание того же хеша не отзывает сессии. Обычный JWT после Logout/смены пароля/блокировки/смены Admin действует до `exp` с учётом clock skew; немедленной DB-проверки access нет.

Миграция владельцев назначает прежним вариантам и справочнику `UserId=-1`: до внедрения auth достоверного владельца не было. Это явная политика учебных данных, не восстановление истории. Добавлены NOT NULL и индексы владельца без постоянного SQL default. При обновлении существующей БД не удалять volume; миграции и demo-bootstrap выполняются при обычном запуске; прочим прежним пользователям нужен явный сброс пароля.

## GraphQL

Единственный открытый бизнес-метод — `login(input: LoginInput!)`. Два взаимоисключающих режима:

```graphql
mutation PasswordLogin($input: LoginInput!) {
  login(input: $input) {
    accessToken accessExpiresAt refreshToken refreshExpiresAt
    user { userId userName userEmail admin }
  }
}
```

Credentials: `{"input":{"email":"ваш-email","password":"ваш-пароль"}}`. Refresh: `{"input":{"refreshToken":"последний-refresh"}}`, поля email/password полностью опустить. Неверный email/пароль/refresh возвращают одинаковый `INVALID_CREDENTIALS`; лимит — `LOGIN_RATE_LIMITED`. Возвращённый access передавать заголовком `Authorization: Bearer ...`. Проверять GraphQL `errors` даже при HTTP200. `Cache-Control: no-store` запрещает кеширование ответов.

Refresh — 256 случайных бит, base64url; БД хранит SHA256, владельца, семейство, сроки, отзыв и ссылку на замену. Ротация сериализована блокировкой строки пользователя и транзакцией PostgreSQL, работает между процессами. Успешная ротация погашает прежний refresh и возвращает новую пару. Повтор погашенного токена отзывает всё семейство, включая выпущенного потомка; независимые входы сохраняются. При потере ответа **не повторять** старый refresh: повтор считается replay, требуется вход с паролем. Срок refresh скользящий от выдачи; абсолютного максимума семейства и автоматической очистки истории пока нет. Сессии переживают restart API.

`logout` защищён access JWT и отзывает его семейство по `sub`/`sid`; повтор безопасен. Чужой session ID не принимается входным аргументом. Новые права при credentials/refresh читаются из Auth, а не из пользовательского input. Открытых Register/Refresh endpoints нет. Схема доступна через `/graphql?sdl` и introspection; IDE открывается по `/graphql`. Доступность схемы не отменяет JWT для бизнес-полей. Для обновления сохранённого снимка публичного SDL есть `tests/Run-ApiTests.ps1 -UpdateSchema`. Необязательный операторский `--export-schema` печатает внутреннюю схему с auth-директивами; публичный SDL их опускает.

JSON-токены предназначены для CLI/нативного клиента с защищённым хранилищем. Не писать их в URL, логи, Git или общее файловое хранилище. Access будущего браузерного клиента держать в памяти; постоянное браузерное хранение refresh/HttpOnly-cookie и CSRF/CORS остаются отдельной задачей WEB-01/FE-AUTH-01. Не сохранять refresh в localStorage как рекомендуемый рабочий flow.

## Правила данных

Пользователь видит/меняет только свои варианты и справочник; администратор — всех владельцев. Владелец при создании всегда текущий пользователь, при редактировании сохраняется, включая редактирование администратором. `CalcVariantInput.userId` имеет Int! = 0 и может быть опущен; прежний ComponentGuideInput.userId остаётся обязательным Int!. Оба совместимых аргумента игнорируются. `admin` не является аргументом Login/профиля. Списки и вложенные ссылки фильтруются в SQL до материализации. Чужой вариант по ID возвращает `null`, его update — `null`, delete — `false`; чужой/отсутствующий componentId во входе даёт `FORBIDDEN`. Печи общие для чтения; их изменяет только администратор.

Снимок состава собственного варианта остаётся видимым, но ссылка `componentGuide` становится `null`, если сам справочник чужой. Чужие `parent`, `parentId`, `children` не раскрываются. Администраторские навигации содержат все доступные записи. `saveTime` хранится в UTC, стабилен при update/restart, у прежних записей неизвестен (`null`).

Обычный CRUD не принимает `isImport=true`. Сохранённый импорт блокирует update с `IMPORTED_DATA_READ_ONLY` и delete с `IMPORTED_DATA_DELETE_FORBIDDEN` для обеих ролей. Это защита действующих API-путей. Полный ORM-инвариант IMP-01, импорт IMP-03 и создание child VAR-01 ещё отдельные задачи; эти возможности не добавлены и их проверки не объявляются выполненными.

Технические основания: [ASP.NET JWT](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0), [Hot Chocolate field authorization](https://chillicream.com/docs/hotchocolate/security/authorization), [RFC9700 refresh rotation](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).
