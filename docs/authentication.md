# Вход, сессии и права

Сначала выполните [обычный запуск](configuration.md), затем войдите по [примеру requests](../requests/README.md). Пользователь `-1` и администратор `-2` создаются автоматически из настроек `DEMO_USER_*` и `DEMO_ADMIN_*`. Повторный запуск сохраняет их пароли и данные. Ручная проверка описана в [manual-auth-check.md](manual-auth-check.md).

## Вход и обновление токенов

`login(input: LoginInput!)` — единственный бизнес-метод без обязательного входа. Он возвращает в JSON токен доступа (`accessToken`, JWT), токен обновления (`refreshToken`), сроки их действия и данные пользователя:

```graphql
mutation PasswordLogin($input: LoginInput!) {
  login(input: $input) {
    accessToken accessExpiresAt refreshToken refreshExpiresAt
    user { userId userName userEmail admin }
  }
}
```

Для входа передайте `{"input":{"email":"ваш-email","password":"ваш-пароль"}}`. Для обновления — `{"input":{"refreshToken":"последний-токен-обновления"}}`, полностью опустив `email` и `password`. Эти режимы нельзя совмещать. Отдельных методов регистрации и обновления токенов нет.

Токен доступа передавайте в заголовке `Authorization: Bearer ...`. Проверяйте поле `errors`, даже если HTTP-код равен `200`. Неверные email, пароль и токен обновления дают одинаковую ошибку `INVALID_CREDENTIALS`; превышение числа попыток — `LOGIN_RATE_LIMITED`. Ответы имеют `Cache-Control: no-store`. Не записывайте пароли и токены в URL, журналы и Git.

При успешном обновлении замените **оба** токена: прежний токен обновления больше не работает. Повторное использование старого токена отзывает всю цепочку его замен, включая последний выданный токен. Независимые входы не затрагиваются. Если ответ потерян, войдите с паролем, а не повторяйте старый токен. Сессии сохраняются после перезапуска API.

`logout` требует токен доступа и отзывает цепочку обновлений текущей сессии по `sub`/`sid`. Повторный выход безопасен. Смена пароля и блокировка отзывают все токены обновления пользователя. Уже выданный токен доступа после выхода, смены пароля, блокировки или смены роли действует до конца своего срока с учётом допуска часов. По умолчанию это 300 секунд и допуск 5 секунд; немедленной проверки его отзыва в БД нет. Новые права читаются из Auth при входе и обновлении токенов.

## Кто видит и меняет данные

Пользователь видит и меняет свои варианты и справочник. Администратор работает с записями всех владельцев. Печи доступны всем для чтения, а создавать, менять и удалять их может только администратор.

При создании сервер назначает владельцем текущего пользователя; при изменении владелец сохраняется, в том числе при работе администратора. `CalcVariantInput.userId: Int! = 0` можно опустить. `ComponentGuideInput.userId: Int!` пока обязателен для совместимости. Сервер игнорирует оба значения. Поле `admin` не принимается при входе или изменении профиля.

Чужой вариант по ID возвращает `null`; его изменение — `null`, удаление — `false`. Недоступный или отсутствующий `componentId` при сохранении состава даёт `FORBIDDEN`. Списки и вложенные связи отбираются по правам в запросах к БД. Чужие `parent`, `parentId`, `children` скрываются. Состав своего варианта виден, но его ссылка `componentGuide` равна `null`, если запись справочника принадлежит другому пользователю. Администратор видит доступные ему связи полностью.

`saveTime` — время создания в UTC, оно не меняется при редактировании и перезапуске. Для старых записей оно неизвестно (`null`).

Обычные операции создания и изменения не принимают `isImport=true`. Уже сохранённый импорт обеим ролям запрещено изменять (`IMPORTED_DATA_READ_ONLY`) или удалять (`IMPORTED_DATA_DELETE_FORBIDDEN`); заменить состав или снять флаг тоже нельзя. Эти проверки действуют в нынешних API-методах. Защита при прямой работе с объектами БД (IMP-01), сам импорт (IMP-03) и создание дочернего варианта (VAR-01) ещё не реализованы.

## Настройки входа

Основные настройки находятся в `Soft/.env`; способ запуска описан в [configuration.md](configuration.md).

| Настройка | Значение и допустимые пределы |
|---|---|
| `JWT_SIGNING_KEY` | случайный секрет не короче 32 UTF-8 байт; используется подпись HS256 |
| `JWT_ISSUER`, `JWT_AUDIENCE` | имена сервера и клиента; шаблон и Compose используют `aglomslag-local`, `aglomslag-clients` |
| `JWT_ACCESS_SECONDS` | срок токена доступа, 1..900 секунд, по умолчанию 300 |
| `JWT_CLOCK_SKEW_SECONDS` | допуск расхождения часов, 0..60 секунд, по умолчанию 5 |
| `JWT_REFRESH_DAYS` | срок токена обновления, 1..30 дней, по умолчанию 7 |
| `AUTH_LOGIN_LIMIT` | 1..1000 проверок в минуту с одного IP соединения, по умолчанию 20 |

Лимит общий для входа, обновления токенов и смены пароля, включая несколько вызовов через псевдонимы GraphQL. За прокси без дополнительной настройки клиенты используют общий IP прокси. Смена ключа подписи делает прежние токены доступа недействительными; токены обновления остаются до отзыва или истечения срока.

Токен обновления содержит 256 случайных бит в формате base64url. БД хранит его SHA256, владельца, цепочку замен и сроки. Обновление выполняется в транзакции PostgreSQL с блокировкой строки пользователя, поэтому одновременные запросы из разных процессов не выдают две действующие замены. Срок отсчитывается от каждой выдачи; общего предельного срока цепочки и автоматической очистки истории пока нет.

HTTP работает во всех окружениях: Docker — `http://localhost:5000/graphql`, порт контейнера `8080`; IDE — `http://localhost:5093/graphql`. Редактор запросов, GET, SDL и introspection доступны публично. Это не даёт доступа к бизнес-полям: кроме `login`, они требуют JWT. Вход в соседнем поле одного документа не авторизует остальные поля.

## Обслуживание аккаунтов

Эти команды не нужны при первом запуске. Используется сервис `bootstrap` профиля `setup`. Далее `docker compose ...` означает `docker compose --env-file Soft/.env -f Soft/Docker-compose.yml`.

| Задача | Что задать в Soft/.env | Команда |
|---|---|---|
| Повторить первоначальное создание демонстрационных аккаунтов | `DEMO_USER_*`, `DEMO_ADMIN_*` | `docker compose ... run --rm bootstrap` |
| Создать обычного пользователя | `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`, при желании `BOOTSTRAP_NAME` | `docker compose ... run --rm bootstrap --bootstrap-user` |
| Сбросить пароль и активировать аккаунт | `TARGET_USER_ID`, `NEW_PASSWORD` | `docker compose ... run --rm bootstrap --reset-password` |
| Заблокировать аккаунт | `TARGET_USER_ID` | `docker compose ... run --rm bootstrap --disable-user` |

Пароль аккаунта — 12..1024 символа, не только пробелы. Команда создания не меняет существующий аккаунт. После обслуживания очистите ненужные временные поля. Сам пользователь меняет пароль через `changePassword(currentPassword,newPassword)` с токеном доступа и прежним паролем.

Автоматическое создание включено по умолчанию в Compose (`DEMO_BOOTSTRAP=true`), вне Compose — выключено. Конфликт email, ID или роли завершает создание с ошибкой и откатывает обе учётные записи. Прежний отключённый аккаунт `-1` с очищенным хешем может быть создан заново. У обеих ролей есть демонстрационный вариант, справочник принадлежит `-1`. Между БД Auth и SlagMode нет внешнего ключа.

## Обновление прежней БД

Перед обновлением сохраните резервные копии обеих БД. Миграции выполняются при обычном запуске; удалять volume не требуется.

Миграция `SecureCredentials` сбрасывает хеши и отключает прежние аккаунты: пароль `Password` больше не работает. Демонстрационный аккаунт восстанавливается автоматически, остальным нужен явный сброс пароля. Миграция владельцев назначает прежним вариантам и справочнику `UserId=-1`, поскольку достоверных сведений о владельцах раньше не было. Это решение для учебных данных, а не восстановление истории. Поля владельца обязательны и индексированы, постоянного значения по умолчанию в SQL нет.

Пароли хранятся как хеши Identity V3: PBKDF2-HMAC-SHA512, 210000 итераций, случайная соль не менее 128 бит. Правильный устаревший хеш V3 обновляется при входе; V2, открытый текст и повреждённый формат не принимаются. Для неизвестного или отключённого аккаунта выполняется проверка той же стоимости. Пароли и хеши не возвращаются в данных пользователя, JWT и сообщениях диагностики.

Триггер миграции `RefreshSessions` отзывает все токены обновления при изменении хеша или блокировке в той же транзакции, включая обновление хеша при входе и прямое изменение через SQL. Повторная запись того же хеша не отзывает сессии.
