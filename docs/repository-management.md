# Правила ведения репозитория

Начать с [карты проекта](../arcitecture.md). Перед правкой проверить `git status --short` и не затирать чужие незавершённые изменения.

## Какой сложности мы ждём от проекта

Это учебное приложение для магистерской работы. Ожидаемый уровень — немного выше средней работы студента магистратуры: оно должно правильно считать, сохранять данные и быть понятным автору. Требований к нему заметно меньше, чем к промышленной системе.

Код и учебные данные не считаются особо секретными. При этом настоящие пароли, ключ JWT и токены не нужно публиковать или записывать в журналы. Проверки входа, владельца данных и ошибок сохраняются: простое приложение тоже должно работать правильно.

Выбирать самое простое решение, которое выполняет текущую задачу. Не добавлять сертификаты, сложную инфраструктуру, дополнительные уровни архитектуры или защиту от всех мыслимых случаев без конкретной необходимости. Повод для усложнения — требование пользователя или воспроизводимая проблема, а не возможность когда-нибудь столкнуться с ней.

Обычный путь пользователя: скачать проект, заполнить один `Soft/.env`, выполнить `docker compose --env-file Soft/.env -f Soft/Docker-compose.yml up -d --build`, открыть HTTP API и работать через `requests`. Подготовка должна занимать несколько минут, без дополнительных обязательных команд.

Документацию писать обычным русским языком. Сначала объяснять, что делать и какой результат ждать. Технический термин использовать только когда он помогает; при первом упоминании коротко объяснять. Точные имена полей, команды и важные ограничения сохранять. Подробности проверки хранить в отчёте задачи, а в повседневной инструкции давать ссылку, не повторять весь отчёт.

## Где хранить файлы

| Каталог / файл | Назначение |
|---|---|
| `Soft/` | Исходники, миграции, DLL, Dockerfile и Compose приложения |
| `requests/` | Схема API, описание полей, запросы и примеры |
| `tests/` | Автоматические тесты и скрипт их запуска |
| `docs/` | Постоянные инструкции по ведению репозитория, настройке и запуску |
| `tasks/TODO.md`, `tasks/TODO_Frontend.md` | Планы сервера и интерфейса |
| `tasks/<ID>/` | Отчёты, разовые проверки и материалы задачи |
| `tasks/<ID>/local/` | Скачанные программы, архивы и временные файлы; вне Git |
| `logs/` | Все создаваемые вручную и runner-файлы `.log`; вне Git |
| `Soft/.env` | Единственный постоянный рабочий env-файл; вне Git |
| `Soft/.env.example` | Единственный безопасный шаблон настроек; в Git |

Не оставлять TODO, отчёты задач, папки `.artifacts*` и журналы в корне, `Soft`, `requests` или `tests`. В корне остаются точка входа `arcitecture.md` и необходимые корневые конфигурации инструментов. Прикладной код и постоянные тесты размещать в соответствующих исходных каталогах, не копировать в `tasks`.

Для новой задачи использовать её ID, например `tasks/SEC-02/verification.md`. Материалы прежних групповых проверок находятся в `tasks/bugfixes/` и `tasks/api-tests/`. Небольшие отчёты и полезные скрипты проверки можно сохранять в Git. Сборки, кэши и скачанные библиотеки хранить в `local/`. Не перемещать файлы внутри чужих данных, Git, SDK или `bin`/`obj` при обычной уборке.

## Журналы и результаты

`tests/Run-ApiTests.ps1` автоматически записывает последний прогон в `logs/last-run.log`. Для отдельного запуска из корня использовать, например:

```powershell
docker compose --env-file Soft/.env -f Soft/Docker-compose.yml build *> logs/SEC-02-build.log
```

В Bash перенаправление эквивалентно `> logs/SEC-02-build.log 2>&1`. Для дополнительных журналов указывать ID задачи и назначение. Не создавать `.artifacts-*.log` или `tests/last-run.log`.

Не печатать пароли, токены и содержимое `.env`. Полный вывод `docker compose config` и `docker inspect` тоже может содержать пароли; для проверки настроек использовать `config --quiet`. Результат кратко записывать в `tasks/<ID>/verification.md`: команда, что получилось и что осталось непроверенным. Удалять только свои временные файлы; хранилище Docker с пользовательскими данными сохранять.

## Настройки и завершение работы

Docker и запуск из IDE используют один `Soft/.env`. Не делать отдельный рабочий env-файл для каждого способа запуска. В Docker адрес БД — `postgres`, с хоста — `localhost`. Настройка и смена пароля: [configuration.md](configuration.md). Временные env-файлы изолированных тестов допустимы только на время проверки и удаляются в `finally`.

После перемещения документов обновлять относительные ссылки, команды и пути в скриптах. Из `arcitecture.md` должны находиться актуальные планы, инструкция настройки и эта инструкция.
