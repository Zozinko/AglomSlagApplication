# SEC-04 — реализация, ожидающая общей проверки

Тесты не запускались: по указанию пользователя сначала родительский агент должен проверить весь интегрированный код. Этот файл описывает реализацию и проверки, а не подтверждает их прохождение. TODO не отмечен.

`CredentialService` использует штатный ASP.NET Core `PasswordHasher<User>`: Identity V3, PBKDF2-HMAC-SHA512, 210000 итераций, случайная соль не менее 128 бит, subkey 256 бит. Параметры штатного hasher задаются в `Program.cs`. Envelope содержит marker, PRF, число итераций и длину соли; успешная проверка более слабого поддерживаемого V3 выполняет rehash. Старый plaintext и Identity V2 не принимаются. Формат дополнительно ограничивает число итераций до 2000000, длину envelope до 1024 символов и размеры соли/subkey, чтобы повреждённая запись не задавала неограниченную стоимость.

Неизвестный пользователь, заблокированный пользователь и неподдерживаемый/повреждённый hash проходят один штатный verify на случайном process-local dummy hash с такими же параметрами. Это выравнивает стоимость KDF; абсолютное время HTTP/SQL не заявляется идентичным. У сохранившихся поддерживаемых V3 с меньшей стоимостью она обновляется при успешном входе. Отдельный executable `tests/credentials` проверяет через recording wrapper фактический envelope и число вызовов KDF; PostgreSQL/GraphQL проверки находятся в `tests/infrastructure/passwords.test.mjs`.

Создание пароля и явная смена требуют 12..1024 символов; полностью пробельные значения отвергаются. Хеш создаётся до передачи сущности EF. Управляемый `--bootstrap-user` использует `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`, необязательный `BOOTSTRAP_NAME` и отказывается менять существующий аккаунт. Он создаёт обычного пользователя, не администратора. Демонстрационные роли и фиксированные ID обеспечивает отдельная команда OWN-01.

Защищённая mutation `changePassword(currentPassword: String!, newPassword: String!): Boolean!` определяет пользователя только по проверенному `sub`; проверяет текущий пароль, блокирует строку `Users FOR UPDATE` и сохраняет новый hash в транзакции. Каждая попытка, включая alias в одном запросе, использует общий с Login лимит по remote IP перед KDF. Управляемый `--reset-password` требует `TARGET_USER_ID` и `NEW_PASSWORD`, явно устанавливает пароль и снимает `Disabled`, чтобы восстановить карантинированные миграцией старые записи. `--disable-user` требует только `TARGET_USER_ID` и ставит `Disabled=true`. Пароль не передаётся аргументом CLI; передавать его через локальное окружение процесса. Обычный запуск не выполняет эти команды. Пустое/некорректное значение не записывается; профиль и Admin не меняются.

Триггер миграции SEC-03 отзывает refresh-сессии в той же транзакции при изменении PasswordHash или включении Disabled. Поэтому смена, операторский сброс, блокировка и rehash отзывают старые refresh-сессии, включая SQL-обновления. Уже выпущенный access JWT действует до короткого срока истечения; новый Login/refresh проверяет Disabled и текущее серверное состояние. В production пароль передаётся по HTTPS; клиентское хеширование не заменяет TLS.

Проверки используют только одноразовых пользователей, созданных operator CLI в изолированном Compose-проекте; cleanup удаляет только их записи Auth и sessions. Пример слабого V3 в тесте строится независимо через Node PBKDF2. Для имитации ранее выпущенной сессии перед увеличением стоимости KDF fixture явно восстанавливает RevokedAt только собственного одноразового пользователя через SQL. Production-сценария снятия отзыва нет.

Интеграция родительским агентом: зарегистрировать scoped `CredentialService` и `PasswordChangeService`; выставить `PasswordHasherOptions.CompatibilityMode=IdentityV3`, `IterationCount=CredentialService.IterationCount`; добавить защищённую mutation; добавить два явных CLI ответвления до открытия HTTP. Runner должен включать файл passwords.test.mjs и после общего review выполнить `dotnet run --project tests/credentials/CredentialChecks.csproj -c Release` в SDK 10.0.402 вместе с API/PostgreSQL-проверками. Для .NET harness в контейнер монтировать весь корень репозитория, чтобы ProjectReference разрешался в `Soft/`.
