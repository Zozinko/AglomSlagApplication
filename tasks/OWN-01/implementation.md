# OWN-01 — реализация для проверки

Дата: 26.10.2026. Задача не отмечена выполненной: автоматические тесты написаны, но по указанию пользователя их запуск отложен до проверки всех изменений родительским агентом.

## Принятые правила

- `CurrentActor` читает `sub` и `admin` из личности, прошедшей JWT middleware; проверка выполняется при обращении к свойствам, чтобы создание корневого Mutation не закрывало анонимный Login.
- `CalcVariant.UserId` обязателен, индексирован, назначается текущим пользователем. Совместимое поле `userId` во входном DTO игнорируется. Обновление, включая администраторское, сохраняет владельца. Те же правила действуют для `ComponentGuide.UserId`.
- Выборка собственных вариантов, справочника, вложенных вариантов печи/справочника, родителей и детей фильтруется в SQL до материализации. Скрытый родитель не выдаётся даже через `parentId`. Снимок компонента собственного варианта остаётся доступным; ссылка `componentGuide` становится nullable и равна null, если справочник принадлежит другому пользователю. Это важно для старых данных и записей, которые администратор связал с чужим справочником.
- Чужой/неизвестный ID записи при update/read даёт null, при delete — false. Чужой либо неизвестный ID справочника в составе сохраняемого варианта даёт FORBIDDEN без раскрытия существования чужой записи.
- Печи общие для чтения. Создание, переименование и удаление общей печи разрешены администратору: обычный пользователь иначе мог бы изменять общие данные других владельцев.
- Импортный оригинал нельзя обновлять (`IMPORTED_DATA_READ_ONLY`) или удалять (`IMPORTED_DATA_DELETE_FORBIDDEN`) через сервис, в том числе администратору. Проверка предшествует обычной валидации payload. Обычные Add/Update отвергают `isImport=true` как VALIDATION_FAILED: признак должен назначаться серверным импортом. Полный ORM-инвариант IMP-01 и команда создания child VAR-01 не реализованы в этой задаче. Будущие entry points должны повторять проверку прав и назначать владельца из текущей личности.

## Хранение и демонстрационные данные

Миграция `20261026125625_VariantOwnership` добавляет nullable-колонку, назначает всем вариантам до внедрения auth владельца -1, приводит прежний недоверенный клиентский `ComponentGuide.UserId` к -1, затем делает колонку обязательной без постоянного default. Сложное восстановление недостоверной прежней истории не выполняется. Это явная политика обновления учебного набора данных, а не угадывание владельца.

Seed содержит исходный вариант -1 владельца -1 с его компонентами, второй демонстрационный вариант -2 владельца -2 без компонентов, общий справочник владельца -1. Auth не читается при построении модели SlagMode.

`DemoUserBootstrap.RunAsync` вызывается только явной командой `--bootstrap-demo` (интеграция Program у родительского агента), создаёт Auth ID -1 и -2 по env `DEMO_USER_EMAIL/PASSWORD`, `DEMO_ADMIN_EMAIL/PASSWORD`; хеширует через SEC-04 CredentialService. Операция выполняется одной Auth-транзакцией, проверяет email/ID/роль, не меняет пароль либо роль уже настроенного активного аккаунта. Явный bootstrap может восстановить только исходный отключённый -1 с пустым хешем после SecureCredentials. Секреты из JSON не принимаются, в исходниках отсутствуют.
