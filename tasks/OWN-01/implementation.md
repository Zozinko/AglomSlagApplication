# OWN-01 — владельцы данных (историческая заметка)

Эта заметка описывает решение до общей проверки: тесты были написаны, но тогда ещё не запускались. Позднее они прошли общий прогон; результат приведён в [отчёте OWN-01](verification.md). Команда `--bootstrap-demo` ниже относится к раннему этапу. Сейчас демонстрационные аккаунты создаются автоматически при обычном запуске; детали есть в [протоколе упрощения](../SEC-02/http-simplification.md).

## Правила доступа

- `CurrentActor` получает `sub` и `admin` из проверенного JWT. Данные читаются при обращении к полям, поэтому публичный `Login` может оставаться доступным.
- У `CalcVariant.UserId` обязателен владелец. Его назначает сервер; входное поле `userId` игнорируется. Обновление записи, в том числе администратором, не меняет владельца. То же правило действует для `ComponentGuide.UserId`.
- Запросы к вариантам, справочнику, печам, родителям и дочерним записям ограничиваются в SQL по владельцу до чтения результата. Чужой родитель не раскрывается через `parentId`. Сохранённые данные компонента остаются доступны, даже если ссылка `componentGuide` скрыта из-за чужого владельца.
- Для чужой или неизвестной записи чтение и обновление возвращают `null`, удаление — `false`. Чужой либо неизвестный справочник в составе варианта даёт `FORBIDDEN`, не раскрывая наличие чужой записи.
- Печи общие для чтения; создавать, переименовывать и удалять их может только администратор.
- Импортные оригиналы нельзя менять (`IMPORTED_DATA_READ_ONLY`) или удалять (`IMPORTED_DATA_DELETE_FORBIDDEN`), в том числе администратору. Обычные Add/Update отклоняют `isImport=true` с `VALIDATION_FAILED`: этот признак назначает серверный импорт.

Полный запрет обхода через ORM (`IMP-01`) и команда создания дочерней записи (`VAR-01`) в эту задачу не входили. Новые способы записи должны применять те же проверки владельца.

## Данные миграции и демонстрационные аккаунты

Миграция `20261026125625_VariantOwnership` добавляет колонку владельца, назначает прежним вариантам владельца -1, затем делает поле обязательным без постоянного значения по умолчанию. Старое недоверенное значение `ComponentGuide.UserId` также заменяется на -1. Недостоверную историю владельцев не восстанавливают; это явное правило для учебных данных.

Начальные данные содержат вариант -1 с владельцем -1 и его компонентами, вариант -2 с владельцем -2 без компонентов, а также общий справочник с владельцем -1. При создании модели SlagMode Auth-БД не читается.

На раннем этапе `DemoUserBootstrap.RunAsync` вызывался командой `--bootstrap-demo`. Он создавал пользователей Auth с ID -1 и -2 из `DEMO_USER_EMAIL/PASSWORD` и `DEMO_ADMIN_EMAIL/PASSWORD`, хешировал пароли через SEC-04 и выполнялся одной транзакцией. Повторный вызов не менял пароль или роль уже настроенного активного аккаунта. Секреты из JSON не принимались и в исходниках не хранились. Сейчас аккаунты создаются автоматически при обычном запуске; прежнюю команду здесь оставляем только для истории.
