# Задачи будущего фронтенда AglomSlagApplication

Дата: 25.10.2026. Это согласованный план интерфейса, а не уже созданное приложение. Backend-задачи и инварианты: [TODO.md](TODO.md); текущие запросы: [requests/README.md](../requests/README.md). При реализации использовать обновлённую схему API после соответствующих backend-задач.

## Общие правила

- Один человек показывает приложение последовательно под обычной учётной записью и администратором. Систему конкурентного редактирования, разрешение конфликтов вкладок и нагрузочные сценарии не добавлять.
- Обычный пользователь работает со своими вариантами; администратор видит и редактирует варианты разных владельцев. Реальные права проверяет API. Переключение локального флага в интерфейсе не должно изображать вход администратором.
- Исторический оригинал с `isImport=true` доступен только для чтения даже администратору. Для эксперимента создавать child с `isImport=false`; ручные варианты можно изменять/удалять по правам и существующим ограничениям связей.
- Пользователь видит исходные параметры перед запуском расчёта. Расчёт получает показанный полный input, серверная команда расчёта только по ID не нужна.
- Предпросмотр импорта и экспорт одного выбранного варианта целиком выполняются в браузере. Серверные preview/confirm/export endpoints и временные серверные черновики для них не требуются.
- Каждая задача ниже имеет способ проверки и критерий готовности. Выбор UI-фреймворка и конкретных клиентских XLSX-библиотек выполнять при начале реализации; текущая задача их не фиксирует.

## [ ] FE-AUTH-01 · P1 · Вход и работа с сессией пользователя/администратора

**Сделать:**

1. Добавить экран Login с понятной ошибкой неверных credentials и состоянием выполнения. Использовать контракт SEC-02/03 и WEB-01, включая выбранный режим refresh.
2. Получать безопасные данные текущего пользователя: ID и признак `Admin`. Подписывать активный аккаунт/режим, чтобы на защите было видно, чьи данные отображаются. При выходе/смене аккаунта очищать старые списки, выбранный вариант и приватные клиентские данные.
3. Передавать access JWT согласованным способом, обычно через `Authorization: Bearer`. Хранить/обновлять refresh согласно принятому контракту; не писать credentials и токены в URL, логи или экспорт.
4. При истечении access выполнить обновление сессии; при отказе refresh вернуть на Login с понятным сообщением. Изменяющие запросы не повторять вслепую после неопределённого сетевого результата: сначала проверить состояние, чтобы не создать второй child/импорт.
5. Подключиться к разрешённому origin по CORS. Скрывать недоступные действия, но обрабатывать и серверный отказ доступа. Проверять GraphQL `errors`, даже если HTTP-статус 200.

**Проверить:** последовательно войти обычным пользователем и администратором на одном компьютере; неправильный пароль, истечение access, отказ refresh, Logout и повторный вход другим аккаунтом. Проверить, что старые записи другого аккаунта не остаются на экране.

**Готово, когда:** интерфейс показывает фактическую серверную личность, авторизованные запросы и обновление сессии работают, ошибки не выглядят успехом и смена аккаунта не оставляет чужие данные.

## [ ] FE-LIST-01 · P1 · Список вариантов со страницами и фильтрами

**Зависимости:** OWN-01, API-01, DTO-01.

**Сделать:** показывать список вариантов, общее количество, текущую страницу и размер страницы. Фильтры: тип записи (все/импортные/ручные), период по дате расчёта, печь и владелец. Пользовательский фильтр доступен администратору; у обычного пользователя фиксируется его область данных.

Фильтры отправлять API, а не применять только к уже загруженной странице. При изменении фильтра сбрасывать страницу на первую. В запросах соблюдать договорённость диапазона дат `[dateFrom, dateTo)` и принятую зону отображения. Элемент списка должен различать импорт/ручной вариант, показывать имя, дату, печь, владельца и наличие родителя в объёме доступного DTO. Обработать пустой результат и ошибки загрузки.

**Проверить:** несколько страниц; каждый фильтр и сочетания; границы дат; отсутствие результатов; переход между аккаунтами. Администратор видит разные `UserId`, обычный — только свои записи, независимо от вручную изменённых параметров запроса.

**Готово, когда:** страницы и количество совпадают с API, фильтры охватывают весь доступный набор, а не только текущую страницу, и ограничения владельца сохраняются.

## [ ] FE-VAR-01 · P1 · Просмотр параметров, расчёт и сохранение Child-варианта

**Зависимости:** VAR-01, IMP-01, OWN-01, BUG-01/02/03/04, DTO-01.

**Сделать:**

1. По выбранному варианту загружать полный набор параметров кокса/шлака/чугуна и компонентов. Показать единицы, владельца, признак импорта, дату, ID и непосредственный `parentId`. Предусмотреть переход к доступному родителю/детям.
2. Загруженный исторический оригинал хранить как исходный снимок. Изменения формы до сохранения относятся к локальному рабочему набору и не должны автоматически отправляться как update оригинала.
3. Кнопка «Рассчитать» отправляет показанные в форме параметры через обычный полный input. Отображать результаты вместе с исходными значениями. После изменения входа помечать прежние результаты как относящиеся к предыдущему набору, пока пользователь не пересчитает; не выдавать старый результат за результат изменённых параметров.
4. Разделить «Сохранить изменения» для доступного ручного варианта и «Сохранить как дочерний». Для child передать `parentId=ID открытого источника`, а не его прежний `parentId`; старый ID не назначается новому варианту. Следовать контракту команды VAR-01 и после успеха открыть возвращённый новый ID.
5. У импортного оригинала обычное сохранение и удаление недоступны для пользователя и администратора. Изменить вводные в рабочей форме можно для расчёта и последующего сохранения child. Объяснить это короткой подписью; доступную кнопку создания child оставить.
6. Разрешить обычное редактирование/удаление ручного child по правам; администратор может работать с чужим ручным вариантом. Для узла с детьми обрабатывать серверный запрет удаления без потери отображаемой истории.
7. При отказе сохранения не показывать уведомление об успехе и не терять введённые значения. Подтверждать успешное сохранение данными ответа API, а не только закрытием формы.

**Проверить:** открыть оригинал, увидеть его данные, изменить вводные, рассчитать, сохранить child и открыть его. Затем создать ещё одну ветвь и child от child, проверить правильные родительские ID. Отредактировать/удалить доступную ручную копию и снова открыть оригинал: он не изменился. Повторить под администратором, включая чужие записи и запреты на импортный оригинал.

**Готово, когда:** пользователь видит, по каким данным выполнен расчёт, различает исходник и рабочую копию, сохраняет правильную ветвь с новым ID и не может изменить историческую запись ни одним действием интерфейса.

## [ ] FE-IMP-01 · P1 · Предпросмотр файла и подтверждение импорта целиком на фронтенде

**Сценарий на пальцах:** выбрать Excel → браузер читает лист `Шлак` → показать, что будет импортировано → пользователь нажимает «Импортировать» → отправить исходный файл обычному API импорта → показать результат записи. До подтверждения импортных данных в БД нет.

**Зависимости:** согласованный mapping IMP-02, обычный приём файла IMP-03, правила OWN-01/IMP-01, WEB-01. **Отдельный API предпросмотра не требуется.**

**Сделать:**

1. Прочитать выбранный XLSX в браузере с помощью подходящей клиентской библиотеки. Проверить лист, ожидаемые заголовки и доступные значения по согласованной версии шаблона. Показать ошибку неподдерживаемого/повреждённого файла без попытки записи.
2. Учитывать матричную структуру: параметры по строкам, варианты по колонкам. Тестовый/рабочий варианты и исторические месяцы не смешивать; предложить выбор печи и области импорта в рамках согласованных options. Формулы/кеш обрабатывать по спецификации IMP-02, не исполнять макросы, внешние ссылки или код.
3. Показать периоды, количество выбранных вариантов, важные входные параметры, печь, владельца текущей сессии, предупреждения и ошибки с координатами. Предпросмотр не является редактором исторических данных: не подменять значения исходного файла незаметно.
4. Хранить выбранный файл и состояние предпросмотра только на клиенте. Отмена или смена файла сбрасывает этот набор, не вызывает mutation и не создаёт серверный черновик. После смены аккаунта повторить выбор/проверку контекста владельца.
5. По явному подтверждению отправить **тот же исходный файл** и соответствующие options в обычный авторизованный endpoint импорта. Не отправлять только клиентское представление как уже проверенные сервером данные. При смене файла/options прежнее подтверждение не должно относиться к другому набору.
6. Учитывать независимую серверную проверку: API может отклонить то, что клиент предварительно показал. Отобразить реальный отчёт импорта, ID/количество сохранённых вариантов, пропущенные повторы и причины отказа; только после ответа обновить список.
7. Проверить соответствие клиентского разбора backend-mapping на одних контрольных примерах. Разные технологии чтения XLSX не должны менять значения процентов, единицы, даты, пустые/нулевые ячейки. Поведение без актуального кеша формулы должно быть одинаково объяснено.

**Проверить:** реальный пример `baseData/Без названия.xlsx`, контрольные ячейки и выбранные месяцы; неверный лист, отсутствующее значение/кеш, нулевой расход, ошибка формулы, смена файла и отмена. Через Network убедиться, что до кнопки подтверждения файл не отправляется на импорт, серверный preview не вызывается, число строк БД не меняется. После подтверждения сверить файл/options запроса, отчёт API и сохранённые значения. Отдельно проверить отказ API после успешного локального предпросмотра.

**Готово, когда:** человек понимает, какие данные собирается загрузить, может отменить действие без записи, а сохранение выполняется только по явному подтверждению через обычный импорт. Весь интерфейс и подготовка предпросмотра находятся на фронтенде, итоговое сохранение и проверка прав остаются на API.

## [ ] FE-EXP-01 · P1 · Экспорт одного выбранного варианта в XLSX/CSV на клиенте

**Согласованный объём:** один выбранный сохранённый вариант; массовый экспорт истории и новый серверный endpoint не требуются.

**Сделать:** сформировать файл в браузере из полного доступного DTO выбранного варианта и результатов, рассчитанных по тому же набору входов. Включить основные параметры, компоненты и расходы, единицы, печь, дату, владельца, ID/`parentId` и признак импорта. Для XLSX сохранить числовые значения как числа; для CSV согласовать разделитель, кодировку и экранирование.

Если форма содержит несохранённые изменения, предложить сохранить вариант/child или отменить изменения перед экспортом сохранённой записи. Если результатов для этого набора ещё нет, явно указать это либо предложить расчёт после просмотра параметров; не выдавать старые результаты за новые. Имя файла сделать понятным, без секретов. Текстовые названия материалов записывать безопасно как текст, не превращать их в формулы.

**Проверить:** экспорт своей записи и доступной администратору чужой записи; импортный оригинал и child; дробные значения, русские имена, запятые/кавычки/переносы в названиях. Открыть полученный XLSX/CSV и сверить число компонентов, входные значения, метаданные и доступные результаты. Проверить, что выгружается одна запись и отсутствуют токены/пароли.

**Готово, когда:** выбранный вариант можно скачать и открыть обычным табличным приложением, данные соответствуют показанному сохранённому набору, а файл создаётся на фронтенде без server-export API.

## [ ] FE-QA-01 · P1 · Подготовить сценарий показа работы

Одному человеку последовательно пройти:

1. Вход обычным пользователем → свои варианты → фильтры/страницы → просмотр входов → изменение и расчёт → сохранение child.
2. Просмотр исходного импортного варианта → невозможность обычного изменения/удаления → доступное создание ручной копии.
3. Предпросмотр Excel → отмена без записи → повторный выбор и подтверждённый импорт → показ отчёта и новых записей.
4. Открытие одного варианта → экспорт XLSX/CSV → проверка файла.
5. Выход → вход администратором → записи разных владельцев → редактирование чужой ручной копии → тот же запрет изменения/удаления импортного оригинала.
6. Ошибка API/истёкшая сессия → понятное состояние интерфейса без ложного успеха.

**Готово, когда:** все сценарии воспроизводимы на учебном стенде одним человеком, привязаны к реальным ответам API и не требуют ручной подмены прав на фронтенде. Предпросмотр/экспорт не считаются реализованными только потому, что backend готов.
