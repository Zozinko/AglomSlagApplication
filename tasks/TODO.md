**Проверено 25.10.2026:** UTC `timestamptz`, стабильные чтения/update/restart, старое время `null`, свежая и обновляемая БД. [Протокол](bugfixes/verification.md).

**Сделать:** в `Soft/DBStructure/Entities/SlagMode/CalcVariant.cs` определить сохраняемое время создания в UTC; настроить EF и добавить миграцию `SlagModeContext`. Обновление варианта не должно переписывать время создания.

**Проверить:** создать вариант, прочитать дважды в разных контекстах, обновить имя, перезапустить API и прочитать снова; проверить SQL и тип столбца. Применить миграцию к существующей и пустой тестовым БД.

**Готово, когда:** `saveTime` стабилен после чтения/обновления/перезапуска, хранится в БД, правило заполнения старых записей документировано.

### [x] SEC-03 · P0 · Реализовать жизненный цикл refresh-токена и проверку владельца

**Выполнено и проверено 26.10.2026:** независимая проверка тимлидом, один финальный прогон: 91/91 Node-тест + .NET CredentialChecks, без ошибок/пропусков. [Протокол](SEC-03/verification.md), [ручная проверка](../docs/manual-auth-check.md). Границы зависимых IMP-01/IMP-03/VAR-01/WEB-01 зафиксированы в протоколе.

**Решение для обсуждения:** чтобы буквально сохранить единственный открытый метод Login, он может поддерживать два взаимоисключающих режима: credentials и refresh. В refresh-режиме обязателен валидный refresh-токен; истёкший access JWT не мешает обновлению. Альтернатива — отдельный Refresh с собственной проверкой refresh-токена; это отдельное исключение из требования «открыт только Login», его нужно согласовать. Не делать Refresh без проверки refresh-токена и не требовать от него ещё действующий access JWT.

**Сделать:**

1. Добавить в Auth-БД сессии: пользователь, хеш криптографически случайного refresh-токена, срок, время создания, отзыв, замена/семейство токенов. Открытый refresh возвращать клиенту, в БД хранить проверяемое производное значение.
2. На обновлении атомарно погашать прежний refresh и выдавать новую пару. Определить обработку повторного использования refresh: повтор не выпускает вторую независимую сессию; подтверждённый replay отзывает семейство. Предусмотреть понятное поведение клиента при потерянном ответе/повторе.
3. Добавить защищённый Logout/отзыв сессии; определить отзыв при смене пароля/блокировке пользователя. Указать, что обычный уже выпущенный JWT без дополнительной проверки живёт до `exp`; если нужен немедленный отзыв access, добавить version/session-проверку.
4. Выбрать клиентское хранение: для браузера рассмотреть Secure HttpOnly cookie с подходящим SameSite и CSRF-защитой refresh-пути; для других клиентов — защищённое хранилище. Не сохранять токены в логах/URL.
5. Получать `UserId` и признак администратора из проверенной сервером личности и применять правила OWN-01. Обычный пользователь работает со своими записями, администратор — с записями всех владельцев; импортные оригиналы неизменяемы для обоих. Клиентские `userId` и `admin` не меняют права. При выдаче/обновлении токенов брать права из Auth-БД, а не из запроса Login.

Ротация и выявление повторного использования описаны в [RFC 9700, §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14). Конкретный формат собственного Login и модель прав остаются проектными решениями.

**Проверить:** refresh после истечения access; неверный/истёкший/отозванный refresh; повтор старого токена, Logout и смена пароля; перезапуск API без потери корректных сессий. Пользователь A не читает/меняет приватные данные B подстановкой ID или `userId`; администратор получает доступ к записям разных владельцев, но не может изменить/удалить импортный оригинал.

**Готово, когда:** сессия обновляется без повторного пароля, ротация и отзыв работают, replay не создаёт рабочую пару, все пути доступа используют проверенную личность и права.

## 5. Защита паролей перед записью в БД

### [x] SEC-04 · P0 · Хранить пароль как стойкий серверный хеш с солью

2. Хешировать на сервере **до передачи значения EF для сохранения**. Пароль передавать по HTTPS; клиентское преобразование не заменяет TLS и серверную проверку. Не использовать обратимое шифрование, простой SHA-256/MD5 или самодельный алгоритм хранения пароля.

Требование защищённого хранения пароля здесь реализуется хешированием, согласно [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

**Готово, когда:** все активные пользователи имеют проверяемый парольный хеш нужного формата, известный seed-пароль не даёт вход в production, credentials не раскрываются клиенту и не сохраняются открытым текстом.

## 6. Сохранение изменённого варианта как дочернего

### [ ] VAR-01 · P1 · Добавить ветвление вариантов через `UpdateCalcVariant`

**Пользовательский сценарий:** пользователь загружает старый вариант, меняет параметры или состав материалов, при необходимости запускает расчёт и выбирает «Сохранить как дочерний». Создаётся новый самостоятельный вариант с указанием непосредственного источника; загруженный вариант и его компоненты остаются неизменными. Из одного источника можно создать несколько дочерних вариантов, а из дочернего — следующую ветвь.

**Текущее состояние:** в `CalcVariant` и EF уже есть nullable `ParentId`, навигации `Parent/Children` и FK с `DeleteBehavior.Restrict`. В `CalcVariantInput` родитель не задаётся; add не заполняет эту связь, update всегда изменяет существующую запись. Поэтому задача требует изменения API и логики сохранения; добавление самой связи в модель повторно не нужно.

**Предлагаемый контракт:** сохранить идею двух режимов `UpdateCalcVariant` и добавить необязательный `parentId` как явный аргумент команды сохранения. Не путать этот аргумент с уже сохранённым `parentId` загруженного объекта: команда определяет **источник новой копии**, а свойство результата — его происхождение. Если выбран вариант с ID 20 и его сохранённый родитель имеет ID 10, для новой копии передать `parentId=20`, а не 10.

| Аргументы команды | Режим и результат |
|---|---|
| `parentId=null`, указан `variantId` | обычное обновление существующего варианта с прежними проверками доступа и защиты импорта; его сохранённый `ParentId` не меняется |
| `parentId` указан и доступен пользователю | создание новой записи; `ParentId` новой записи равен этому ID, переданный `variantId` не используется как PK и не обновляется |
| `parentId` указан, но родителя нет или нет права использовать его | понятная ошибка; не переходить к обычному update и не создавать несвязанный корневой вариант |
| оба ID отсутствуют | ошибка аргументов; для создания нового корневого варианта остаётся `AddCalcVariant` |

Разрешить не передавать `variantId` в режиме создания дочернего, например сделав аргумент nullable с серверной проверкой комбинации. Существующие вызовы update с ID должны продолжать работать. `parentId=0` — попытка сослаться на конкретный ID, а не обозначение отсутствия; отрицательные seed-ID тоже являются реальными идентификаторами. Для обычного редактирования дочернего варианта клиент явно передаёт `parentId=null`, не копируя всё тело ответа query в команду сохранения.

**Где:** `Soft/AglomSlagServer/GraphQL/Mutations/Mutation.cs`, `Services/SlagModeQueryService.cs`, при необходимости отдельный DTO команды, `Soft/DBStructure/Entities/SlagMode/CalcVariant.cs` и конфигурация контекста; примеры и описание в `requests`. Учесть BUG-01, BUG-03/04, IMP-01 и SEC-03.

**Сделать:**

1. Ввести явное разделение режимов. Ветка с `parentId` использует логику добавления (`AddCalcVariantAsync` с поддержкой родителя или общий метод создания); ветка без него — `UpdateCalcVariantAsync`. Проверку существования/доступа к родителю и инварианты держать в сервисе/слое записи, чтобы их нельзя было обойти прямым вызовом сервиса, а не только в GraphQL resolver.
2. В режиме дочернего создать **новый** экземпляр `CalcVariant` и новые экземпляры `ComponentVariant`, заполненные переданными пользователем отредактированными значениями. Не менять tracking-состояние источника на добавленное, не переиспользовать его навигационные коллекции и не вызывать `RemoveRange` для исходного состава.
3. Не переносить `VariantId` загруженного объекта в новую сущность. Если ID пришёл в аргументе или DTO, в этой ветке не назначать его PK. Новый ключ генерирует БД; компоненты связываются с новым вариантом. Их `ComponentId` по-прежнему ссылаются на справочник, но `VariantId` относится к новой записи. Не ожидать от sequence значения «родитель + 1»: возможны пропуски и другие вставки.
4. Установить `ParentId` равным ID **непосредственно редактируемого источника**, а не его корневого предка. Проверить существование родителя, право чтения/создания производного варианта, печь и все ссылки компонентов. В режиме update не позволять случайно перепривязать существующую запись к другому родителю. Новый узел не должен создавать цикл или ссылаться сам на себя.
5. Сохранять полный снимок данных: входные параметры кокса/шлака/чугуна, дату расчёта, имя и весь список компонентов. Если input остаётся полным, отсутствие обязательного поля — ошибка, а не скрытая подстановка нуля. Новое время сохранения формировать на сервере в UTC по BUG-01; владелец — текущий пользователь по принятой модели прав. Расчёт и сохранение остаются отдельными операциями, автоматический пересчёт не добавлять неявно.
6. Для пользовательской копии импортированного источника устанавливать `IsImport=false` на сервере: это новый рабочий вариант, а не исходная импортная запись. Сохранить `ParentId` на импортный оригинал с его `IsImport=true`; его данные и флаг не менять. Клиентский флаг из загруженного оригинала не должен случайно сделать ручную копию импортом или снять защиту исходника. Создание настоящего импорта остаётся отдельным доверенным путём.
7. Сохранить новый вариант и компоненты атомарно. При ошибке/исчезновении родителя не оставлять дочерний вариант без связи и не менять оригинал. Вернуть новый ID, `parentId`, время сохранения, флаг и корректно загруженные поля результата. Клиент после сохранения должен переключиться на возвращённый ID; дальнейшие сохранения определяются выбранным режимом, а не старым ID формы.
8. Сохранить FK `Restrict`: удаление источника с дочерними вариантами не должно каскадно уничтожать историю. Возвращать понятную ошибку использования. Ручную копию без зависимостей можно удалять по обычным правилам; импортный оригинал защищён IMP-01 независимо от наличия детей. Для просмотра происхождения обеспечить корректное чтение `parentId`, `Parent/Children` через существующие query или явные резолверы по BUG-04.

**Проверить:**

1. Создать исходный вариант с компонентами, сохранить его полный снимок из API/SQL. Загрузить, изменить один параметр и расход материала, сохранить с `parentId=исходный ID`. Проверить новый ID, точную связь с источником и сохранение новых значений. Полный снимок источника до/после должен совпасть, включая его компоненты, дату и время сохранения.
2. Повторить с `variantId=ID источника` и с другим переданным `variantId`: ни одна существующая запись с этим ID не обновляется, вставка использует новый ключ БД. Повторить без `variantId` в режиме дочернего; отдельно проверить обычный update при `parentId=null`.
3. Создать двух детей одного источника, затем ребёнка первого ребёнка. Проверить дерево: оба первых узла ссылаются на источник, следующий — на непосредственно выбранного ребёнка. Сохранение и изменение одного узла не изменяют соседние и предыдущие снимки.
4. Создать ручной child из `IsImport=true` источника: оригинал остаётся защищённым и неизменным, новый child имеет `IsImport=false` и правильный родительский ID. Проверить обычное редактирование/удаление копии и невозможность изменения/удаления оригинала через эту команду.
5. Проверить отсутствующего/недоступного родителя, оба отсутствующих ID, `parentId=0`, действительный отрицательный seed-ID, неверные ссылки компонентов и отказ записи. При отказе число вариантов/компонентов не меняется. Проверить право создания копии для двух разных пользователей по выбранной политике общих/приватных данных.
6. Попробовать удалить родителя с детьми: получить доменную ошибку, все узлы и компоненты остаются. Проверить query происхождения, ответ mutation с печью и компонентами, перезапуск API и повторное чтение дерева.

**Готово, когда:** пользователь проходит сценарий «загрузить → изменить → сохранить как дочерний → открыть новый вариант»; БД выдаёт новый ID, `ParentId` указывает на выбранный источник, исходные данные полностью сохранены. Обычный update сохраняет прежний режим, копии не обходят защиту импорта и права доступа, связи дерева и ответы API корректны. Наличие `parentId` в схеме без этих проверок не закрывает задачу.
