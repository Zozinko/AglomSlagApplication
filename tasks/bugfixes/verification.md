## Итоговая проверка

Команда из корня: `./tests/Run-ApiTests.ps1`. Окружение: Node.js 24.13.1, Docker Desktop Linux containers, SDK 10.0.402, ASP.NET 10.0.13, EF CLI 10.0.12, PostgreSQL 16.15; образы закреплены digest.

Расширенный набор: **47 HTTP-тестов и 9 последовательных инфраструктурных тестов — 56 всего**. Финальный runner возвращает 0 только после успешных тестов и удаления своего Compose-проекта. SDL сверяется с сохранённым файлом; его намеренное обновление выполнялось отдельно через `-UpdateSchema`.

Собирается Release текущих исходников, миграции применяются к свежей PostgreSQL в `tmpfs`. Отдельная БД `ApiUpgrade` создаётся на схеме до багфиксов, получает дополнительную старую запись, затем обновляется до последней версии. Повторная миграция и `has-pending-model-changes` проверяются отдельно. Ошибок компиляции нет; прежние `CS8618` Aglom оставлены по прямому исключению этой области пользователем. В шлаковых DTO и новых output DTO предупреждения устранены.

## BUG-12: источник нуля и точность

Исследованы исходники адаптера и открытые типы/свойства DLL через reflection и прямой вызов, без декомпиляции или восстановления закрытого кода. В описании DLL `UBF_Slag.S` обозначен как содержание серы в шлаке, %. Раньше во входных данных этого поля не было, поэтому `BaseSlag.S` оставался 0. В открытом эксперименте `BaseChugun.S=0.016` и `BaseSlag.S=0/0.16/0.32` дали `LS_Fact=0/10/20`. После исправления те же результаты получены через полный набор полей HTTP-ответа.

Добавлены `slag.s: Float! = 0` и `slagSContent: Float! = 0`. Вариант хранит новое значение в `real`; миграция `20261025093431_AddSlagSulfurContent` задаёт старым строкам 0 для сохранения прежнего **вычислительного допущения**. Это не восстановленное историческое измерение. Для фактического коэффициента клиент должен передать измеренную серу шлака. Новое поле проходит валидацию процентов.

`slagOut` и `balSlagMass` оба читают `MassOfOxSlagSum`; значение между чтениями не меняется. Это два имени одного результата. `caOBalSlagMass` читает отдельный `UdWeight`. Оснований считать эти два имени разными физическими балансами нет.

Для обычных чисел IEEE-754 binary32 ошибка записи и повторного чтения ограничена `|x|·2^-24` (с запасом на JSON и арифметику binary64 в тесте). Пример с точно представимыми двоичными входами сохраняет **весь** результат расчёта без изменений. Десятичный пример проверяет границы каждого сохранённого входа, суммы и входной температуры. Для положительного отношения серы выведена граница `|ratio|·2u/(1-u)`, где `u=2^-24`; это не допуск, подобранный под наблюдавшееся число.

Для остальных непрозрачных нелинейных результатов тест выводит наблюдаемые before/after/delta, не объявляя их универсальным научным допуском. Предметная верификация математических DLL не заявляется; оснований менять все `float/real` на `double` по одному примеру нет.

## Почему BUG-08 не закрыт целиком

Пользователь не задал численных рамок, но указал проверку здравого смысла: жидкий металл не должен быть холоднее своей температуры плавления. Публичные API трёх шлаковых DLL не предоставляют liquidus/solidus или функцию температуры плавления по составу. `TChugMin/Max` в другой модели — изменяемые настройки, а не такая функция.

Температура фазового перехода зависит от состава сплава: в первичном [исследовании Fe-C-Si и многокомпонентных чугунов](https://www.mdpi.com/2075-4701/11/5/846) показана зависимость от Si и других элементов. Подставлять температуру плавления чистого железа или один порог эвтектики для всех входов было бы неверно. Реализована только строгая физическая граница абсолютного нуля. Для закрытия остатка нужны поддерживаемая фазовая модель/диапазон составов либо явно выбранный инженерный порог. Принятие input пока не означает подтверждение его жидкого состояния.

## Найденное при интеграции

Первый build прошёл, но живой запуск выявил разделение DI Hot Chocolate/application: исправлена factory регистрации фильтра. Docker Desktop при restart меняет случайный host-port: тестовый клиент теперь заново получает адрес. SDL выдаётся как bytes при загрузке PowerShell: runner сохраняет UTF-8 без преобразования массива байтов в строку чисел и проверяет начало схемы. Эти проблемы устранены до финальной проверки.

Дополнительная проверка записи и повторного чтения совпала с намеренной остановкой тестовой БД другим инфраструктурным тестом; её заменили последовательным полным прогоном. Штатный runner выполняет эти этапы по очереди.
