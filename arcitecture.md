# Как устроен AglomSlagApplication

Это карта проекта для автора и разработчиков. Она описывает существующий код, а будущие работы находятся в [TODO](tasks/TODO.md). Имя файла `arcitecture.md` оставлено прежним, чтобы не ломать ссылки.

Проект учебный: ожидаемый уровень немного выше средней магистерской работы. Нужны правильные расчёты, сохранность данных и понятный код. Промышленная инфраструктура и сложная защита сами по себе не являются целью. Подробнее — [правила проекта](docs/repository-management.md).

## С чего начать

1. Для запуска открыть [настройку](docs/configuration.md): заполнить `Soft/.env` и выполнить одну команду Docker.
2. Для работы с API открыть [примеры запросов](requests/README.md).
3. Перед изменением кода прочитать [правила проекта](docs/repository-management.md), проверить `git status --short` и местные `AGENTS.md`, если они появились.
4. Найти метод в `GraphQL/Queries/Query.cs` или `GraphQL/Mutations/Mutation.cs`, затем перейти к его сервису.
5. Названия и типы полей сверять с [схемой API](requests/schema.graphql), их смысл — со [словарём полей](requests/contracts.md).

```powershell
docker compose --env-file Soft/.env -f Soft/Docker-compose.yml up -d --build
```

После запуска доступен `http://localhost:5000/graphql`. Страница GraphQL, схема и список полей открыты всем. Бизнес-методы, кроме `login`, требуют токен. Демонстрационные пользователи создаются автоматически из `.env`; дополнительные команды для первого входа не нужны.

## Основные части

Сервер принимает запрос GraphQL и вызывает нужный сервис. Сервис либо обращается к PostgreSQL через Entity Framework Core (EF), либо передаёт данные математической DLL.

- `AglomSlagServer` — единственное постоянно работающее .NET-приложение.
- `DBStructure` — библиотека с таблицами и двумя классами подключения: `SlagModeContext` и `AuthContext`.
- `SlagModeSolver` — библиотека подготовки шлакового расчёта, без обращения к БД.
- Математические DLL выполняют сами расчёты. Не менять их и не придумывать внутренние формулы по внешнему результату.

Решение `Soft/AglomSlagServer/AglomSlagServer.slnx` включает все три проекта. Исторически некоторые пространства имён отличаются от папок: сервисы используют `AglomGraphQL.Api.Services`, методы чтения — `AglomSlagServer.Queries`, изменения — `AglomSlagServer.Mutations`. Это не отдельные приложения.

## Запуск и настройки

| Контейнер / сервис | Назначение | Ожидаемое состояние |
|---|---|---|
| `aglom_postgres` / `postgres` | PostgreSQL с БД `SlagMode` и `Auth` | `healthy`, порт хоста 5432 |
| `aglom_migrator` / `migrator` | Обновляет структуру обеих БД | Завершён с кодом 0 |
| `aglom_graphql_api` / `graphql-api` | API | Работает, порт хоста 5000 → порт контейнера 8080 |

Compose сначала ждёт PostgreSQL, затем успешные миграции и только потом запускает API. После проверки обеих БД сервер создаёт demo-аккаунты, если включён `DEMO_BOOTSTRAP`. В Compose он включён по умолчанию. Сервис `bootstrap` с профилем `setup` нужен лишь для необязательных команд обслуживания.

Рабочий файл настроек один — `Soft/.env`. Docker получает из него переменные окружения. Внутри сети Docker адрес БД — `postgres:5432`, с хоста — `localhost:5432`. При запуске из IDE в режиме Development тот же файл читает `Startup/LocalEnvironment`; уже заданные переменные процесса важнее файла. Другой путь можно указать через `AGLOMSLAG_ENV_FILE`. В Production сам сервер env-файл не читает.

`DatabaseConfiguration` собирает строки подключения через NpgsqlConnectionStringBuilder. Поддерживаются прежние имена: сначала `ConnectionStrings__SlagModeContext` / `ConnectionStrings__AuthContext`, затем `CONNECTION_SLAG` / `CONNECTION_AUTH`, затем отдельные `DB_*`. Если подключение любой БД не работает, API завершает запуск с кодом 1 до открытия порта. При вызовах инструментов EF эта проверка пропускается.

Данные сохраняются в volume `postgres_data` (обычно `soft_postgres_data`). Обычные `up`, build и restart их не удаляют. `down -v` удаляет. Init SQL создаёт обе БД только при первом запуске пустого хранилища. Смена пароля роли PostgreSQL требует изменить пароль в самой БД, а не только в `.env`: [инструкция](docs/configuration.md).

Для IDE нужен SDK, а не только .NET runtime:

```powershell
dotnet restore Soft/AglomSlagServer/AglomSlagServer.slnx
dotnet run --project Soft/AglomSlagServer --launch-profile http
```

Адрес IDE-запуска — `http://localhost:5093/graphql`. Обычный Docker-запуск не требует установки .NET на хосте.

## Вход и права

`Auth/CredentialService` проверяет серверные хеши паролей. `AuthService` выдаёт токен доступа JWT и токен обновления refresh. `RefreshSessionService` хранит сессии в Auth-БД и заменяет использованный refresh новым. Пароль, его хеш и refresh не входят в JWT.

`CurrentActor` получает ID и признак администратора из проверенного JWT. Обычный пользователь видит свои варианты и справочник. Администратор видит данные всех владельцев. Печи доступны для чтения всем вошедшим, изменяет их только администратор. Владелец новой записи назначается сервером; переданный `input.userId` не даёт сменить владельца.

`logout` запрещает дальнейшее обновление этой сессии. Уже выданный access JWT действует до `exp`: по умолчанию около 5 минут с допуском времени 5 секунд. Это принятое поведение, немедленный отзыв access не требуется. Пароли demo-аккаунтов не сбрасываются при обычном restart.

Полные настройки и поведение сессий: [вход и токены](docs/authentication.md). Подключение будущего браузерного клиента с другого origin (адреса сайта) относится к WEB-01.

## Как API читает и сохраняет данные

Hot Chocolate строит схему из C#: `GetBlastFurnaces()` становится `blastFurnaces`, входной `InputDataModel` — `InputDataModelInput`. Идентификаторы имеют тип `Int`, числа `float` и `double` представлены типом `Float`. Регистр полей важен: например, `caO`, `siO2`, `feOinAgl`.

Схема скачивается с `/graphql?sdl`; именно её хранит `requests/schema.graphql`. Необязательная команда `--export-schema` показывает внутреннюю схему и может дополнительно содержать служебные auth-директивы. Сервер не читает файл схемы из `requests` как настройки.

`SlagModeQueryService` выполняет чтение, создание, изменение и удаление. `SlagModeOutputReader` загружает нужные связи несколькими SQL-запросами. Ограничения владельца применяются в БД до получения строк. У `Program.cs` две фабрики EF-контекстов с пулом 128; сервис создаёт и освобождает свой контекст для каждого вызова, не делит его между параллельными запросами.

Ответы API отделены от классов таблиц: `BlastFurnaceOutput`, `ComponentGuideOutput`, `CalcVariantOutput`, `ComponentVariantOutput`. Это объекты данных (DTO), чтобы новое внутреннее поле БД случайно не появилось в API. Mapperly переносит одинаковые поля, а связи собираются явно. Ошибки RMG012/RMG020 при таком переносе останавливают сборку.

Ссылки `BlastFurnaceReference`, `ComponentGuideReference`, `CalcVariantReference` содержат поля без обратных списков. Так ответ не разрастается в бесконечную цепочку «родитель → дети → родитель». Для полного варианта нужен `calcVariantById`. Чужие `parent`, `parentId`, `children` скрываются; `componentGuide` в собственном снимке состава может быть `null`, если справочник чужой.

Страниц списка, сортировки и пользовательских фильтров пока нет. SQL-загрузка также не меняется автоматически от набора полей в GraphQL-запросе: `AddProjections`, `AddFiltering`, `AddSorting` не подключены.

## Таблицы и правила сохранения

PostgreSQL содержит две отдельные БД. Между ними нет внешних ключей и общей операции отката.

| БД / таблица | Что хранится | Важные связи |
|---|---|---|
| `SlagMode.BlastFurnaces` | ID и название печи | Используемую печь удалить нельзя |
| `SlagMode.ComponentsGuide` | ID, владелец и состав материала | Используемую запись справочника удалить нельзя |
| `SlagMode.CalcVariants` | ID, владелец, печь, даты, имя, `IsImport`, составы кокса/шлака/чугуна | Есть необязательный `ParentId`; родителя с детьми удалить нельзя |
| `SlagMode.ComponentVariants` | ID варианта/компонента, имя, расход и копия состава | Пара `(VariantId, ComponentId)` уникальна; состав удаляется вместе с обычным вариантом |
| `Auth.Users` | ID, имя, email, хеш пароля, `Admin`, `Disabled` | Email уникален |
| `Auth.RefreshSessions` | Хеш refresh, пользователь, сроки, отзыв и замена | Сессии связаны с пользователем Auth |

Здесь `SlagMode.X` означает «таблица X в базе SlagMode», а не отдельную SQL schema. Таблицы находятся в `public`; имена с заглавными буквами требуют кавычек, например `SELECT * FROM "CalcVariants"`.

Состав содержит `FeContent`, `SiO2Content`, `Al2O3Content`, `CaOContent`, `MgOContent`, `SContent`, `MnOContent`, `TiO2Content`. Компонент варианта хранит собственную копию: изменение справочника не меняет старый расчёт. Повтор одного `ComponentId` внутри варианта запрещён.

При сохранении проверяются печь, доступные компоненты, уникальность их ID, имена и дата UTC. Update полностью заменяет редактируемые поля и состав, сохраняя владельца и время создания. `components: []` очищает состав. Всё сохраняется целиком либо остаётся без изменений. Обычный CRUD не принимает `isImport=true`; уже сохранённый импорт нельзя изменить или удалить ни одной роли.

`SaveTime` — время создания UTC, не меняется при update/restart. У старой истории и начальных записей оно `null`, потому что точное время неизвестно. `CalcDate` также передаётся в UTC, например `2026-01-01T00:00:00Z`. В БД составы используют `float` / PostgreSQL `real`, в расчёте — `double`: возможна небольшая погрешность. Единицы и проценты автоматически не пересчитываются.

Начальные данные задаются миграциями: печь `-1`, справочник `-1..-8`, вариант пользователя `-1` с шестью компонентами и вариант администратора `-2` без компонентов. Пользователей `-1/-2` создаёт запуск API из `.env`, не `HasData`. Отрицательный ID — настоящая запись, а не обозначение отсутствия.

`ParentId/Parent/Children` уже хранятся и читаются, но команда создания дочернего варианта ещё относится к VAR-01. Не добавлять её в документацию как работающую возможность. Нет также проверки версий при одновременном редактировании: для учебного сценария она не требуется.

## Изменения БД

Миграции лежат отдельно в `DBStructure/Migrations/SlagMode` и `DBStructure/Migrations/Auth`. Не смешивать их и не переписывать уже применённые файлы как способ обновить существующую БД.

Важные последние изменения: `PersistVariantSaveTime` сохраняет время, `AddSlagSulfurContent` — серу шлака, `VariantOwnership` — владельцев. В Auth `SecureCredentials` отключает прежние аккаунты с ненадёжными паролями и очищает хеши, а `RefreshSessions` добавляет сессии и их отзыв при смене пароля/блокировке. Demo-аккаунт восстанавливается автоматически; другим прежним пользователям нужен явный сброс пароля.

Мигратор сначала обновляет SlagMode, затем Auth. Если второе обновление не прошло, первое автоматически не отменяется; повтор применит недостающие изменения. Сам API миграции не запускает.

Для разработчика, если нужна новая миграция:

```powershell
dotnet tool restore
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet ef migrations add MeaningfulChange --context SlagModeContext --project Soft/DBStructure --startup-project Soft/AglomSlagServer --output-dir Migrations/SlagMode
# Для Auth заменить контекст на AuthContext и папку на Migrations/Auth.
```

Проверять новую и уже заполненную тестовую БД. Команды подключения и смены паролей — в [настройке](docs/configuration.md).

## Расчёты

### Агломерат

Путь: `Mutation.CalculateAglom` → `AglomCalculationService` → `AglomCalculatorService` из DLL → `AglomCalculationResult`. Вход включает шихту, флюсы `LIMESTONE`/`DOLOMITE`, кокс, золу и параметры агломерата. `FeOinAgl` передаётся в поле DLL `FeOInAgl`; единицы не меняются.

`createPreset` пока игнорируется, расчёт не сохраняется. `result.id` равен переданному `userId`, это не ID записи и не право доступа. Прежние задачи агломерата исключены пользователем: не объявлять их исправленными. Численный алгоритм DLL неизвестен.

### Шлак

Путь: `Mutation.CalculateSlagMode` → `SlagModeCalculationService` → `SlagModeSolver.GetTableData` → DLL UBF/SlagSolver → `OutputSlagMode`. БД в расчёте не участвует; сохранить вход нужно отдельной командой варианта.

Проверяются обязательные данные, обычные конечные числа (не NaN/Infinity), непустой состав, расходы не меньше нуля, положительная сумма расходов, проценты 0–100 и `SiO2 > 0` в делителе. Температура выше абсолютного нуля, но это **не** проверка жидкого состояния шлака: согласованной модели здесь нет. Проверяется весь результат, а не только запрошенные поля.

Solver заполняет `BaseChugun`, `BaseSlag`, `BaseKoks`, `BaseShihta`, вызывает `SetPartOfZhRM`. CaO, SiO2, TiO2 и S передаются в `BaseSlag`; CaO, SiO2, Al2O3, MgO также участвуют в отдельном `SlagSolver.Solve`. Результаты библиотек объединяются, температура и текущая вязкость получаются через `UBF_Functions`.

`totalMat` — сумма расходов. `materialParts` — вложенный список `{key,value}`, где доля материала равна его расходу, делённому на сумму. `slagOut` и `balSlagMass` берутся из одного `MassOfOxSlagSum`, это два имени одного результата. `castIronTemp` возвращает `iron.temp`, а `slagTemperature` рассчитывается отдельно.

`slag.s` и сохраняемое `slagSContent` передают фактическую серу, %. Оба можно опустить: значение по умолчанию 0 сохраняет прежнее поведение, но не означает измеренный исторический ноль. Проверенный пример DLL: `(S)=0.16/0.32`, `[S]=0.016` даёт `sDistribution=10/20`. Это не доказывает правильность всех непрозрачных формул. Погрешность хранения и подробности: [отчёт расчётов](tasks/bugfixes/verification.md), [поля и единицы](requests/contracts.md).

## Ошибки и проверки

Ожидаемые ошибки имеют короткие коды: `VALIDATION_FAILED`, `REFERENCE_NOT_FOUND`, `REFERENCE_CONFLICT`, `FORBIDDEN`; отказ DLL или NaN/Infinity в шлаковом результате — `CALCULATION_FAILED`. Отсутствующая или чужая запись при чтении/update обычно даёт `null`, при delete — `false`. Проверять GraphQL `errors` даже при HTTP 200.

Клиенту не возвращаются SQL, пароль и стек исключения. Development добавляет только безопасный тип исключения и SQLSTATE (код ошибки PostgreSQL). В серверном журнале также нет сырых запросов/секретов. Подробное логирование EF/Npgsql отключено. Отдельных систем журналирования и readiness здесь нет.

[Тесты](tests/README.md) вызывают настоящий API и PostgreSQL в отдельном Docker-проекте. Они проверяют все 19 методов, права, сессии, сохранение и отказ записи без потери данных. .NET-проверки паролей лежат в `tests/credentials`. Математические проверки подтверждают соединение с DLL и отдельные свойства результата, а не всю научную модель.
